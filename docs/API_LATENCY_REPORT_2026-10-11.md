# 약 API 캐시 개선과 사용자 화면 지연 보고서

작성일: 2026-10-11, 한국·일본 시간 UTC+9. 운영 서버 확인 버전: **0.1.9**.

실제 검색·상세 화면과 운영 API를 사용하는 Android 에뮬레이터에서 72회 측정했다. 기존 처리 경로를 재현한 조건과 비교하면 검색 실행 후 결과가 그려지는 시간은 중앙값 **420 → 274ms(엣지 캐시), 22ms(로컬 캐시)**였다. 자동 검색은 **800 → 700ms, 414ms**, 상세 내용의 첫 프레임은 **524 → 437ms, 78ms**였다. 상세 화면 전환까지 완료되는 시간은 **614 → 595ms, 595ms**로 차이가 작았다.

이 결과는 통제된 에뮬레이터 실험이다. 사용자의 실제 휴대폰이나 이동통신 환경에서 얻은 수치, 사용자 대상 체감 조사 결과는 아니다.

## 1. 요청 시작과 사용자에게 적용되는 시점

주 지표는 **앱이 사용자의 검색 실행·마지막 입력·상세 열기 동작을 처리하기 시작한 시점부터, 결과 데이터가 반영된 첫 화면 프레임의 래스터화 완료 시점까지**다. 서버 내부 처리시간이나 응답 헤더 도착 시간만으로 끝내지 않는다. 응답 본문 전체 수신, JSON 처리, 새 로컬 캐시 저장, 데이터 매핑, 상태 반영, 화면 프레임 생성·래스터화를 포함한다.

자동 검색은 마지막 입력 이벤트부터 측정하므로 실제 코드의 400ms 대기를 포함한다. 상세 열기는 화면 이동 시작부터 측정하므로 상세 위젯 생성까지의 시간도 포함한다. 사용자 동작은 실제 화면의 콜백/화면 이동을 측정 도구에서 호출했으며, 물리 터치부터 앱 이벤트 전달까지의 시간과 디스플레이에 실제 빛이 나오는 시점은 측정하지 않았다.

상세 화면은 전환 애니메이션 도중에도 데이터가 그려질 수 있다. 이를 과장하지 않기 위해 **내용이 반영된 첫 프레임**과 **내용 반영 및 화면 전환 모두 완료된 프레임**을 별도로 제시한다. 첫 프레임은 텍스트의 사람 눈 기준 가독성이나 모든 사진 다운로드 완료를 보장하는 지표가 아니다.

종료 시각은 Flutter `FrameTiming.rasterFinishWallTime`을 사용했다. 결과 상태 반영 이후에 build가 시작된 첫 프레임을 선택하고, 타이밍 콜백이 모아서 전달되는 지연은 포함하지 않았다. 이 값은 프레임 래스터화 완료 시각이다. [Flutter FramePhase 공식 문서](https://api.flutter.dev/flutter/dart-ui/FramePhase.html)

## 2. 기존 방식과 현재 방식

기존에도 식약처 데이터를 저장하는 **서버 D1 캐시**는 있었다. 모든 검색이 매번 식약처까지 가는 구조는 아니었다. 다만 앱에서 같은 검색이나 같은 상세를 다시 요청하면 서버까지 다시 왕복했고, Worker의 일반 처리 경로와 D1 조회를 거쳤다. 서버 D1 캐시가 없거나 만료되면 식약처 API를 호출했다. 상세는 식별 정보와 소비자 설명 API를 병렬로 호출하고 결과를 합쳤다.

기존 경로:

`사용자 동작 → 입력 대기(자동 검색만) → 앱 HTTP 요청 → Worker 일반 처리/D1 캐시 조회 → 필요한 경우 식약처 조회 → JSON 처리 → 화면 반영`

현재 경로:

`사용자 동작 → 입력 대기(자동 검색만) → 앱 로컬 캐시 확인 → 없으면 HTTP 요청 → Cloudflare 엣지 캐시 확인 → 없으면 기존 D1/식약처 경로 → JSON 처리 및 로컬 저장 → 화면 반영`

| 계층 | 적용 내용 | 보관 조건 | 적중 시 생략되는 작업 |
| --- | --- | --- | --- |
| 앱 로컬 | 공개 약 검색·상세 JSON, 메모리 및 SharedPreferences 저장 | 검색 1시간, 상세 24시간; 최대 100개·2MiB | 해당 약 API의 네트워크 요청 전체 |
| Cloudflare 엣지 | 공개 GET 약 검색·상세 응답 | 설정 TTL 1시간; 캐시가 더 일찍 제거될 수도 있음 | 일반 API 처리, 해당 요청의 D1 조회·요청 제한 DB 처리·D1 모니터링 기록 |
| 기존 서버 D1 | 식약처 조회 결과 | 기본 유효 기간 24시간; 외부 API 실패 시 기존 데이터의 만료 후 최대 7일 대체 정책 | 식약처 재조회 |

로컬 캐시는 동시 중복 요청을 합치고, 만료·손상 데이터를 제외하며, 저장 실패 시 메모리로 동작한다. 엣지는 정상적인 완전한 공개 응답만 저장하며 인증·쿠키 등으로 개인화될 수 있는 요청은 우회한다. 엣지 데이터는 같은 데이터센터에서 같은 캐시 키로 조회하는 사용자들이 재사용할 수 있다. 검색어·페이지·한 번에 조회하는 개수 등이 다르면 다른 항목이다.

**서버 엣지 캐시는 운영에 적용됐다. 앱 로컬 캐시는 새 앱 빌드에 포함돼야 사용자의 설치 앱에도 적용된다.** 현재 구버전 앱이 바로 얻는 효과는 엣지 캐시 효과다. 로컬 캐시 적중은 앞서 같은 항목을 조회했고 아직 유효한 경우에 해당한다.

## 3. 사용자 동작부터 결과 첫 프레임까지

단위 ms, 각 조건 6회 측정의 중앙값. 1,000ms = 1초. 기존 경로는 현재 운영 서버에서 엣지를 `Cache-Control: no-cache`로 우회하고 앱 캐시를 끈 비교 조건이다. 과거 버전 전체를 되돌려 측정한 역사적 실측값은 아니다.

| 사용자 동작 | 기존 경로 재현 | 엣지 적중·로컬 미적중 | 앱 로컬 적중 | 엣지 단축 | 로컬 단축 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 검색 실행 / 키보드 검색 | 420ms | 274ms | 22ms | 146ms (34.8%) | 398ms (94.8%) |
| 마지막 글자 입력 후 자동 검색 | 800ms | 700ms | 414ms | 100ms (12.5%) | 386ms (48.3%) |
| 약 상세 열기 | 524ms | 437ms | 78ms | 87ms (16.6%) | 446ms (85.1%) |

자동 검색의 로컬 적중도 414ms인 이유는 약 400ms의 입력 대기를 유지하기 때문이다. 캐시가 충분히 빨라도 현재 설정에서는 마지막 입력 직후 결과가 나오지 않는다. 검색 실행 콜백은 이 대기를 거치지 않는다.

상세 화면에서 **내용과 화면 전환 모두 완료**되는 시점은 다음과 같다.

| 상세 열기 → 전환 완료 및 데이터 반영 프레임 | 기존 경로 | 엣지 적중 | 로컬 적중 |
| --- | ---: | ---: | ---: |
| 중앙값 | 614ms | 595ms | 595ms |
| 기존 대비 단축 | — | 19ms (3.1%) | 19ms (3.1%) |

측정 Flutter 버전의 Android 기본 전환은 450ms로 설정돼 있다. 실제 측정에는 프레임 대기와 렌더링이 추가돼 약 600ms가 걸렸다. 데이터 조회와 전환 애니메이션은 겹쳐 진행되므로 API 시간과 애니메이션 시간을 단순히 더하면 안 된다. 앱 테마의 전환 방식 및 기기가 바뀌면 이 결과도 달라진다.

입력 대기 및 화면 생성 이전 시간을 제외하고, **약 조회 처리 함수 시작 → 결과 첫 프레임**을 기준으로 보면 다음과 같다. 로컬 적중에는 실제 HTTP 전송이 없으므로 여기의 요청 시작은 앱 내부 조회 요청 시작이다.

| 조회 처리 | 기존 경로 | 엣지 적중 | 로컬 적중 |
| --- | ---: | ---: | ---: |
| 검색 실행 / 키보드 검색 | 420ms | 274ms | 22ms |
| 마지막 글자 입력 후 자동 검색 | 399ms | 297ms | 10ms |
| 약 상세 열기 | 510ms | 431ms | 65ms |

## 4. 지연이 어디서 발생했는지

아래 열은 각각의 중앙값이다. 표본마다 단계 길이가 다르므로 각 열의 중앙값을 더해 주 지표의 중앙값을 재구성할 수는 없다. 네트워크 열은 HTTP 전송 시작부터 본문 전체 수신까지다. 데이터 준비 열은 사용자 동작부터 앱에서 표시할 데이터가 준비되기까지이며 입력 대기·네트워크·JSON 및 필요한 캐시 저장을 포함한다. 마지막 열은 데이터 준비 이후 첫 결과 프레임까지다.

| 동작 | 조건 | 조회 시작 전 대기 | 네트워크 본문 수신 | 동작 → 데이터 준비 | 데이터 준비 → 첫 프레임 |
| --- | --- | ---: | ---: | ---: | ---: |
| 검색 실행 / 키보드 검색 | 기존 경로 | 0.0ms | 312ms | 312.0ms | 115.2ms |
| 검색 실행 / 키보드 검색 | 엣지 적중 | 0.0ms | 174ms | 195.1ms | 81.8ms |
| 검색 실행 / 키보드 검색 | 로컬 적중 | 0.0ms | 요청 없음 | 0.3ms | 21.3ms |
| 마지막 글자 입력 후 자동 검색 | 기존 경로 | 401.4ms | 305ms | 706.1ms | 94.9ms |
| 마지막 글자 입력 후 자동 검색 | 엣지 적중 | 402.8ms | 201ms | 614.2ms | 80.2ms |
| 마지막 글자 입력 후 자동 검색 | 로컬 적중 | 402.4ms | 요청 없음 | 402.6ms | 9.5ms |
| 약 상세 열기 | 기존 경로 | 14.1ms | 314ms | 329.8ms | 183.9ms |
| 약 상세 열기 | 엣지 적중 | 12.6ms | 169ms | 192.1ms | 255.3ms |
| 약 상세 열기 | 로컬 적중 | 16.2ms | 요청 없음 | 18.4ms | 62.8ms |

엣지 상세에서는 네트워크가 약 314 → 169ms로 줄어도 전체 첫 프레임은 524 → 437ms로 줄었다. 이번 에뮬레이터에서 전환 중의 렌더링 지연과 프레임 변동이 있었다. 응답이 빨라진 비율을 화면의 체감 개선 비율로 그대로 옮길 수 없는 사례다.

새 `PublicApiCache` 객체가 저장한 캐시 값을 복원하는 조건도 측정했다. 검색 실행 **20ms**, 자동 검색 **415ms**, 상세 첫 프레임 **89ms**였고 약 API 요청은 모두 0회였다. 다만 같은 프로세스에서 이미 초기화된 SharedPreferences 값을 읽는 조건이다. **앱을 완전히 종료·재실행하는 시간이나 첫 디스크 읽기 지연을 측정한 값은 아니다.** 저장 캐시 전체가 100개·2MiB에 가까울 때의 복원 시간도 별도 측정하지 않았다.

## 5. 사용자가 느낄 수 있는 차이

- **같은 검색 재실행:** 약 0.42초 → 0.02초. 로컬 적중에서는 네트워크 로딩 대기가 대부분 사라져 즉시 바뀌는 느낌에 가까워질 것으로 예상된다.
- **자동 검색:** 엣지 적중은 약 0.80초 → 0.70초로 약 0.10초 단축이다. 로컬 적중은 약 0.41초까지 줄지만 현재 400ms 입력 대기가 체감 속도를 제한한다.
- **같은 약 상세 다시 열기:** 내용의 첫 프레임은 약 0.52초 → 0.08초로 앞당겨진다. 로딩 표시 대신 상세 내용이 전환 초반부터 준비되는 이점이 있다. 하지만 전환이 끝나는 시간은 약 0.61초 → 0.60초라, 화면 이동 전체가 크게 빨라졌다고 평가하기는 어렵다.
- **기존 설치 앱의 엣지 효과:** 검색 실행 기준 약 0.15초, 상세 첫 프레임 기준 약 0.09초가 줄었다. 기다림을 줄이는 개선이지만 모든 화면이 즉시 뜨는 수준은 아니다.

위 체감 표현은 측정값과 화면 동작을 근거로 한 해석이다. 사람을 대상으로 전후 체감 시험을 진행한 결과는 아니다. 최초 조회, 새로운 검색 키, 캐시 만료·제거, 새로운 연결, 통신 상태가 나쁜 경우에는 이번 적중 수치보다 오래 걸릴 수 있다.

## 6. 아직 개선되지 않은 구간

| 구간 | 현재 처리 | 이번 캐시 효과 및 측정 상태 |
| --- | --- | --- |
| 인증 번호 6자리 입력 | 입력 완료 시 자동 인증 시작 | 인증 완료 버튼을 누르는 동작을 없앴다. 사람의 클릭 시간은 측정하지 않았다. |
| 인증 시작 → 로그인 후 홈 | 인증 API → 세션 저장 → 온보딩 설정 → 서버 스냅샷 다운로드 → 로컬 병합 → 서버 업로드 → 홈 진입 | 약 캐시 적용 대상이 아니다. 인증된 실제 로그인 전후 지연은 미측정이다. 홈 전환 설정은 일반 조건에서 560ms이며 네트워크 총시간을 뜻하지 않는다. |
| 로그인 후 데이터 동기화 | 계정별 GET/PUT 요청; 충돌 시 추가 요청 가능 | 이번 공개 약 캐시로 줄어드는 구간이 아니다. |
| 약국 등 다른 API | 기존 각 API 처리 | 이번 약 검색·상세 캐시 적용 범위에 포함되지 않는다. |
| 약 사진 | 별도 `Image.network` 요청 및 이미지 디코딩·렌더링 | JSON 캐시는 사진 파일을 포함하지 않는다. 이번 지표는 사진 전체 다운로드 완료 시간이 아니다. |
| 식약처까지 가는 완전한 미적중 | 엣지 및 D1에 없는 데이터를 외부 API에서 조회 | 서버 캐시를 삭제하지 않았으므로 통제된 첫 조회의 화면 지연을 별도 측정하지 않았다. |

로그인→홈의 정확한 지연 숫자를 약 API 지연에서 추정해 적지는 않았다. 이 구간은 네트워크 호출이 연속으로 진행되는 구조이므로 다음 개선 후보는 로그인 성공 후 홈 표시와 동기화 대기 구조의 조정이다. 계정 변경 시 데이터가 섞이지 않도록 기존 계정 전환·병합 규칙을 유지해야 한다.

검색 체감의 다음 후보는 로컬 적중 시 400ms 대기를 줄이거나 생략하는 방식, 상세 체감의 다음 후보는 화면 전환 길이·렌더링 비용 조정, 사진의 다음 후보는 별도 이미지 캐시 및 미리 불러오기다. 이 보고서를 위해 이 동작들은 추가로 변경하지 않았다.

## 10. 실제 수정한 핵심 코드

속도와 동작을 바꾸는 핵심 네 가지를 발췌했다. 아래 코드는 각 함수 내부의 일부이며, 전체 구현과 유효성 검사는 연결된 원본 파일에서 확인할 수 있다.

**① 약 조회에 로컬 캐시를 연결** — [api_client.dart](/Users/kimrasng/dev/pillnote/lib/services/api_client.dart:129)

```dart
final response = await _cache.getOrLoad(
  key: uri.toString(),
  ttl: const Duration(hours: 1),
  load: () async => _asMap(await _transport.requestUri('GET', uri)),
  cacheable: (response) =>
      response['data'] is List && _isFreshDrugResponse(response),
);
```

기존의 직접 HTTP 호출을 `getOrLoad`로 감쌌다. 캐시가 유효하면 저장된 응답을 반환하고, 없을 때만 `load`의 HTTP 요청을 실행한다. 검색은 1시간, 상세는 같은 방식으로 24시간 보관한다. 전체 URI를 키로 사용해 서버 주소·검색어·페이지·조회 개수가 다른 응답을 구분하고, 오래된 대체 응답이나 불완전한 상세는 저장 대상에서 제외한다.

**② 저장된 캐시를 먼저 읽고 중복 요청을 합침** — [public_api_cache.dart](/Users/kimrasng/dev/pillnote/lib/services/api/public_api_cache.dart:39)

```dart
await (_initialization ??= _restore());
final entry = _entries.remove(key);
if (entry != null && entry.isFresh(_now())) {
  _entries[key] = entry;
  return _decode(entry.payload);
}
final pending = _pending[key] ??= _load(key, ttl, load, cacheable);
```

처음 사용할 때 저장된 캐시를 복원하고, 유효한 항목이면 네트워크 없이 반환한다. 같은 키의 요청이 동시에 들어오면 `_pending`에 보관한 작업 하나를 공유한다. `_decode`는 조회마다 별도 응답 객체를 만들어 화면에서 데이터를 수정해도 다음 조회에 영향을 주지 않게 한다.

새 응답은 `SharedPreferences.setString`으로 저장하며 최대 **100개·2MiB**를 유지한다. 만료된 항목을 제거하고 한도를 넘으면 오래 사용하지 않은 항목부터 비운다. 저장·복원 실패가 약 조회 실패로 이어지지 않도록 예외를 처리했다.

**③ 엣지에 응답이 있으면 D1 처리 전에 즉시 반환** — [edge-cache.js](/Users/kimrasng/dev/pillnotebackend/src/edge-cache.js:73)

공개 약 검색·상세 GET만 대상으로 삼고, 아래 조건의 요청은 캐시를 우회한다.

```javascript
if (request.method !== 'GET'
    || ['authorization', 'cookie', 'origin'].some((name) => request.headers.has(name))
    || /(?:no-cache|no-store)/i.test(request.headers.get('cache-control') ?? '')) return null;
```

`cache.match(target.key)`로 응답을 찾은 뒤 유효하면 여기서 반환한다.

```javascript
const expiresAt = Number(cached.headers.get(EXPIRES_HEADER));
if (expiresAt > now()) return clientResponse(cached, 'HIT', request);
```

이 조기 반환이 서버 지연을 줄이는 핵심이다. Worker에서 기존 서버 처리를 감싸도록 연결했기 때문에 적중한 요청은 `fetchOrigin()`과 그 안의 D1 처리를 거치지 않는다. 키에는 서버 호스트, 배포 버전, 약 식별자 또는 검색 조건을 반영한다.

미적중 시 기존 경로로 조회한 정상 응답을 다음 코드로 저장한다.

```javascript
waitUntil(cache.put(target.key, stored).catch(() => {
  console.warn(JSON.stringify({ event: 'drug-edge-cache-write-failed' }));
}));
```

`waitUntil`로 저장 작업을 이어가므로 캐시 쓰기 완료를 기다리며 응답을 붙잡지 않는다. 읽기 실패 시에는 기존 경로를 실행하고, 쓰기 실패 시에는 성공한 조회 응답을 그대로 유지한다. 오류·불완전한 상세·개인화될 수 있는 응답은 엣지에 저장하지 않는다.

**④ 인증번호 6자리 입력 시 자동 인증, 중복 실행 방지** — [verification_code_field.dart](/Users/kimrasng/dev/pillnote/lib/widgets/verification_code_field.dart:207), [verification.dart](/Users/kimrasng/dev/pillnote/lib/screen/register/verification.dart:202)

입력 위젯에서 6자리가 채워지면 완료 콜백을 호출한다.

```dart
onChanged: (code) {
  if (code.length == 6) widget.onCompleted?.call(code);
},
```

인증 화면은 이 콜백을 기존 인증 처리 함수에 연결한다.

```dart
onCompleted: (_) => _handleVerify(),
```

인증 함수 시작에는 다음 가드를 두어 인증 진행·번호 재전송·이전 화면 복귀 중 중복 요청을 막는다.

```dart
if (_isReturning || _isLoading || _isResending) return;
```

버튼을 누르는 단계를 없앤 변경이다. 인증 API와 로그인 후 동기화 자체의 처리 시간을 줄이는 코드는 아니다.
